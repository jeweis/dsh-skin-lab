# dsh-skin-lab

主题插件：**10 套内置主题 + 自由组合配色与背景图**，全部在设置里的独立一页完成。其中 6 套是抽象色彩场，4 套是手绘水彩插画（同一场景的白天 / 夜晚两版）。

不依赖官方工具链：**没有 npm 依赖、不需要构建仓库、不需要安装 TypeScript**。`src/` 是零依赖 ES module，`node scripts/build.mjs` 把它们拼成 `lib/client.js`。

## 设计决策

### 背景图是「抽象色场」，不是摄影场景

第一版我生成了 6 张摄影味的图（雾中松林带月亮、bokeh 光斑、冰晶枝叶）。**它们都不合格**：一张风景照会引入**焦点**和**高频细节**，而焦点就是在和界面内容抢注意力——右上角一轮亮月，压在上面的任何文字都会被它吃掉。

现在的美术语言是平滑的大面积渐变**色场**：没有焦点、没有高频结构、任何裁切都成立、永远不会和文字打架；只在「纸墨」一张上保留纸纹，其余不留材质。顺带两个实际收益：**平滑渐变放大不糊**（1600×900 在 4K 上依然干净），以及**低细节图 JPEG 压得更小**（抽象六套共 339 KB，每张两版）。

构图上也刻意对齐了界面结构：亮部集中在**右侧内容区**，安静或深色的一侧留给**左侧栏**。深色版另有一条额外约束——辉光必须柔和，不能形成刺眼的高光（原因见下面「可读性是算出来的」）。

第三轮又换掉两张，依据不是看素材本身，而是**把插件自己的设置页真的渲染出来看**——这一步之前做不到，只能靠数值推断：

| | 症状 | 定量证据 | 替换后 |
| --- | --- | --- | --- |
| 霜白 | 在主题卡片和缩略图里退化成一块空白 | 亮度跨度 p05–p95 只有 **34 级**（216→250），整张挤在 `#f0f5fa..#cfe6f5` | 跨度 **60 级**（193→253），颗粒 0.542→**0.227** |
| 松林 | 竖向光带像模糊伪影 | **96.7 KB**，而同样 1600×900 q82 的深海 28.8、极光 36.1、余烬 37.9 KB——多出来的字节全是噪点（颗粒度 1.518） | 颗粒 **0.253**，体积 **19.5 KB**，对角线光扫清晰 |

结论：「颗粒」不是美术语言，是缺陷。平滑色场本就该压得很小，**体积异常本身就是缺陷信号**——这一条比看眼睛更早发现问题。

### 每个主题出两张图，而不是一张图加一层纱

第一版每个主题只有一张图，另一模式靠自动遮罩补偿。**这是整个插件最大的设计错误**，而它被一个看起来合理的机制掩盖了：纱确实能让深图在浅色界面上可读，但**纱变不出结构**。四套深色主题在浅色模式下被洗成同一片淡青灰，主题身份只剩配色——那已经不是设计好的那套主题了。

而且这个错误是**对称**的，我当时只想到一半：纸墨和霜白两张浅色图在深色模式下同样被黑纱糊掉。

正解不是把纱调强，而是**画出缺失的那张图**。现在每套主题两张：同一条构图规则（左侧安静给侧栏、右侧明亮给内容）、同一个色相家族，但一张是高调的浅色版、一张是低调的深色版。

配对之后自动遮罩的公式**一个字都不用改**。它按「图与当前模式的错配量」计算，而配对图的错配量天然是 0——浅色图 mean ≥ 0.68、深色图 mean ≤ 0.30，都落在舒适区之外。于是它从「给内置主题打补丁的拐杖」退回它本该有的角色：**只服务用户自己上传的那一张图**，因为那一张没有配对可换。

一个连带简化：主题预设不再带 `veil` 值。以前 ink 是 18、ember 是 34，因为那时纱在干活；配对之后那只是「预先糊上一层」，而遮罩这个控制权本来就应该完全属于用户。现在六套预设都用中性的 30，`veil` 也从预设里删掉了（省略即取默认值）。

### 可读性是算出来的，不是看出来的

浅色界面写近黑的字，深色界面写近白的字，所以两种模式的失败方向**相反**：

- 浅色模式：取决于图里**最暗的 5%**——近黑文字压在那里会消失；
- 深色模式：取决于图里**最亮的 5%**——近白文字压在那里会消失。

`prepare-assets.py` 因此为每张图量出 `mean / p05 / p95`，验收时把这两个尾部与每套主题**自己的字色**做 WCAG AA 比对（`verify.mjs` 里的 `every built-in theme keeps its own text legible in BOTH colour schemes`）。

这条检查写出来之前，六套深色图里有**四套不合格**：按平均值算是 8.8–11.9 : 1（看起来全过），按最亮 5% 算只有 **2.3–3.9 : 1**。深海与霜白的亮部会把正文吃掉——而那正是我上一轮还写进 README、声称「为深色设计」的几张图。**平均值掩盖了亮部。**

修法是给亮部设硬上限（由 4.5:1 反推得 ≤ 约 0.41 亮度）：辉光保留，但改成不刺眼的柔和泛光。现在的实测最坏值：

| | 浅色模式（对最暗 5%） | 深色模式（对最亮 5%） |
|---|---|---|
| 六套主题的范围 | **7.41 – 11.46 : 1** | **5.21 – 11.08 : 1** |

副产品：压暗后的图 JPEG 压得更好，素材总量反而从 397.5 KB 降到 **338.6 KB**。

### 插画可以画，但主体必须小

上一节那条「不要焦点」如果读成审美洁癖，就会挡住插画。它其实可以量化：决定可读性的是明度分布的**尾部**，而尾部只由**占比**决定。规矩于是能重写成一条可执行的：

> 大面积的对比结构会压低 p05、抬高 p95；而占比远小于 5% 的亮点或暗点，动不了这个统计量。

具体到画面：**猫的眼睛、窗上的一小块月光、几颗星、几只萤火虫、远处的小船——都安全**；真正危险的是"整片深色树林"或"一大团高光"。所以插画族每张都按同一套构图纪律生成：

- 主体放在**右下三分**，左半边与中间留成**几乎没有细节的水彩空白**——那正是对话文字待的地方；
- 亮部 / 暗部只允许出现在**占比远小于 5%** 的细节上；
- 白天版按「整张没有比 65% 更暗的地方」要求，夜晚版按「整张没有比 38% 更亮的地方」要求。

结果是这四套的实测**比抽象色场还安全**：

| | 明度均值 | 关键尾部 | 对自家字色 |
|---|---|---|---|
| 四张白天版 | 0.932 – 0.945 | p05 **0.788 – 0.867** | 9 : 1 以上 |
| 四张夜晚版 | 0.067 – 0.096 | p95 **0.106 – 0.161** | 8 : 1 以上 |

所以它们**一点遮罩都不需要**（`veil` 取中性的 30），插画按原样铺满整页。这才是「细节要小」这条纪律的价值：它不是把画面变无聊，而是让画面能在界面后面**全强度**存在。

代价是体积——插画有真实的水彩纸纹理，压缩率远不如平滑色场，八张多出 778 KB。

### 上传过大时自己压，不要退回给用户

壁纸最终要作为 `data:` URL 存进 `localStorage`（整个源约 5 MB），所以图片确实有上限，一张手机照片就超了。**第一版的做法是拒绝，然后告诉用户「请先压缩，或改用图片地址」。**这是错的：图已经解码在这个页面里，一次 canvas 重编码只是一帧的工作量，没有理由把它推回给用户。

现在的行为：

- **放得下就原样存**，一个字节都不动——小图永远不会因为重编码掉画质；
- **放不下就自己压**，按一条降级阶梯逐档尝试，取第一个放得进预算的结果；
- **压完会说明**：`已自动压缩：2.1 MB → 18 KB（256 × 256）`，因为"为什么我的图看起来不一样了"不该等用户来问。

阶梯每档是一次完整降采样（最长边 2560 → 2048 → 1664 …，质量 0.86 → 0.82 → …），取第一个放得进去的。用**真实 JPEG 编码器**实测：一张 2333 KB / 1672×941 的 PNG 在第 1 档就落到 **193 KB**（对预算有 10 倍余量）；一张 1200 万像素手机照大约在第 2 档落到 2048×1536 / 约 1.6 MB。两个结果都比「让用户自己去压」更好。

两个细节值得写明：

- **透明图先铺一层主题表面色再编码**。JPEG 没有 alpha，留空的 canvas 会编码成黑色——不铺底的话，一张带透明度的 PNG 壁纸会变成黑底。
- **阶梯会折叠重复档位**。源图本来就小于上限时，每档缩放后的像素数相同，那就没有理由用更低的质量把同一张图重编码七次。

**走不通的两条路**说清楚，免得当成 bug：粘贴的 `data:` 地址背后没有文件，https 地址的字节在别人服务器上——两者都无法在这里重编码，所以那条路径仍是明确拒绝，并且会**指向会自动压缩的文件上传**。

**验收能覆盖到哪、覆盖不到哪**：阶梯的形状、预算比较、目录折叠都由纯函数断言；整条流程由一个桩 canvas 跑通（它的输出体积对面积与质量单调，因此循环终止的理由和真实浏览器一致）。但**真实浏览器的解码与编码路径没有端到端测过**——把文件喂给那个 `<input type=file>` 需要用户或 CDP，本机做不到。这一条如实记在「边界与已知不确定」里。

### 配色用 OKLab 混色，不用 sRGB
64 个 token 全部由锚点派生，派生用的插值空间决定了它们好不好看。sRGB 插值是在 gamma 编码后的字节上走直线，所以中间调必然发灰发脏：

```
sRGB  中点  #808080   ← 视觉上偏亮
OKLab 中点  #636363   ← 感知上正好一半（相对亮度 0.125）
```

OKLab（Ottosson 2020）是感知均匀空间，所以等步长看起来等步长：文字的四级淡出是一条**均匀的阶梯**，强调色往表面上的着色不会变成灰泥。这是「设计过」和「换了颜色」的分界。

### 锚点的三条纪律

1. **表面色接近中性**，只带一丝主题色相，靠**明度**区分气质而不是靠饱和度。饱和的表面色会让主题看起来像一块色布；身份应该由强调色承担。
2. **强调色自信但略降饱和**，明暗两套分别调整（深色模式更发光，浅色模式更沉稳）。
3. **按钮文字按对比度选，不按习惯。** 用填充色的相对亮度对比 **0.179**——黑白文字对比度相等的那个点——亮强调色配深色文字，深强调色配白字。这条修掉了一个真实缺陷：原来的阈值是 0.55，会给亮青 `#4cc9dd` 配上白字，几乎看不清。现在有断言强制每个配色的按钮文字都过 **WCAG AA（≥4.5:1）**。

### 只发真实存在的 token

`verify.mjs` 内嵌了一份从本机 rc.2 主题产物里读出的 token 清单，断言**插件能发出的每一个名字都在清单里**（当前 74 个，0 个臆造）。拼错一个名字（比如 `--dsw-alias-bg-layer-4`）会直接失败，而不是静默无效。

核实过程中避开了一个坑：`--dsw-linear-gradient-think` 名字像品牌渐变，实际是 `linear-gradient(180deg,#fff 20%,#fff0 100%)`——**是渐隐蒙版**，改它会破坏思维链的渐隐，所以刻意不动。而 `--dsw-gradient-onboarding-*-stops` 是真正的品牌色标列表，现在按主题强调色生成：

```
--dsw-gradient-onboarding-blue-stops: <深> 20%, <强调> 51%, <浅> 85%, <深> 100%
```

### 背景画在 `html` 上；遮罩只服务「用户自己的那一张图」

`html` 的背景会传播到 canvas，天然位于所有应用表面之下，不需要 z-index 技巧；配 `background-attachment: fixed` 图片不随内容滚动；`body` 背景置透明。

内置主题走的是**配对选图**：按 `color-scheme` 选出为该模式画的那一张，遮罩为 0——图按原样呈现。所以下面这套机制的实际服务对象是**用户上传的单张图**，以及任何「图与当前模式不匹配」的情况。

**遮罩（scrim）不能是一个固定值。** 释放后的页面表面是**透明**的，而界面的正文在浅色模式下是**近黑色**、深色模式下是**近白色**——所以一张深色图配浅色界面，等于**把近黑文字放在深色照片上**，直接不可读。

而错配量**本身就不对称**：深色图在深色模式下需要 **0** 遮罩（那是设计意图，遮一点就毁了），在浅色模式下需要 **0.72**。所以遮罩必须同时取决于**图片自己有多亮**和**当前是哪一种明暗**：

```
明度 L（图片实测均值）
浅色模式遮罩 αL = clamp((0.68 − L) / 0.32, 0, 0.72)      // L 够亮就是 0
深色模式遮罩 αD = clamp((L − 0.30) / 0.30, 0, 0.72)      // L 够暗就是 0
```

明度由 `scripts/prepare-assets.py` 在处理时就量好写入 `src/assets.js`（运行时无法在不解码的前提下读 `data:` URL 的像素）。留意这条公式对**配对的内置图恒为 0**：浅色图 mean ≥ 0.84、深色图 mean ≤ 0.16，都在阈值之外。这正是「配对」和「遮罩」两件事可以并存而不打架的原因——公式一个字没改，只是不再有内置主题需要它。

用户上传的图没有实测值，按**未知明度 0.5** 处理，两种模式各加约 0.56 / 0.67 的纱，这是它的保底可读性。界面上的「遮罩浓度」是**微调**（30 为不干预）：往下调最多到 0，但**自动部分仍在**，所以用户不可能把可读性调没。

CSS 上写成两遍：第一遍是普通深色纱（所有引擎都认），第二遍用 `light-dark()` 读取应用已设在 `html` 上的 `color-scheme`，且**两侧的 alpha 不同**。选图用的也是同一个 `color-scheme`（`getComputedStyle(document.documentElement).colorScheme`），并用 `MutationObserver` 监听它变化——**图、纱、设置页的画廊三者因此永远在同一个判断上**，不会互相错位。

守这件事的断言有两条：一条要求**每套内置主题在两种模式下遮罩都为 0**（配对完整性），一条把每张图的最暗/最亮尾部与该模式自己的字色做 **WCAG AA** 比对（可读性，见上文「可读性是算出来的」）。

**透明化保留配色色相**：释放的表面是 `rgba(该配色原本的值, α)` 而不是中性灰。若配色选「官方」（读不到官方的表面值），退回中性半透明铬色——否则面板不透明、图被挡住。

### 高度用平台的 `--dsw-elevation-*`，不是 `--dsw-shadow-*`

rc.2 里现代阴影是 `var(--dsw-elevation-stroke), 0 4px 16px 0 #00000008, …`——**第一层是从 `--dsw-elevation-stroke` 取来的 1px 描边环**。所以替换值保留这个环、只改衰减：表面保住清晰的边，同时获得不同的景深。而且 `--dsw-elevation-stroke-color` 默认取 `var(--dsw-alias-border-l4)`，我改了 border-l4，**描边环自动跟着主题走**，不用额外接管。

四种阴影：跟随官方 / 柔和浮起 / 扁平（仅描边）/ 品牌光晕（环与光晕都取自强调色）。纸墨主题用扁平——**纸不该投影**。

### Logo：槽位锚点不生成盒子，别在它上面画东西

renderer 会在每个槽位容器上打 `data-slot="<key>"`（rc.2 renderer 产物 1100 行），官方图标用 `currentColor` 绘制——所以给 `[data-slot="sidebar.brand.mark"]` / `[data-slot="sidebar.brand.name"]` 设 `color: var(--dsw-alias-brand-primary)` 就能染色，不碰标记、不争插槽所有权。

**但那个锚点带内联 `display: contents`**（renderer 1094 行 `ANCHOR_STYLE`），它是个纯寻址钩子、**不生成盒子**。这一点让三道规则里只有一道天然成立：

| 规则 | 为什么 |
|---|---|
| `color` 染色 | ✅ `color` **可继承**，能穿过 `display:contents` 抵达子元素 |
| `width/height/background-image` | ❌ 需要盒子，设在锚点上被静默忽略 |
| `display:none` 隐藏字标 | ❌ `display` 写在**内联**样式上，普通规则赢不了 |

第一版自定义 Logo 就是踩在这里：鱼被正确隐藏了、染色也生效了，**只有用户那张图不出现**——而失效的恰好是需要盒子的那一条。两处都用 `!important` 越过内联样式（这是唯一能越过内联的手段），并把锚点本身变成槽位已经预留好的 24px 盒子；占位内容用 `>*` 隐藏，**不按名字点名 `svg`**——填充槽位的是外壳，不是这个插件，规则不该依赖它填的是什么。

这类 bug 无法靠"断言我写出的字符串"发现，所以验收里加了一条**平台探针**：从 `DSH_HOME` 读真实安装的 renderer 与 sidebar 产物，断言「锚点确实钉在 `display:contents`」与「两个槽位 key 确实存在」。哪天外壳不再这样锚定，探针会失败，`!important` 就能按计划退休，而不是悄悄活过它的理由。

### 设置页由它正在应用的那套配色绘制

页面里每一个颜色都是 `--dsw-alias-*` token，所以**选主题的界面本身就被主题染色**——这是最直接的反馈。token 表达不出的浅色调（选中环、悬停底色）用 CSS `color-mix()` 就地算出来；万一引擎不支持，降级是「没有那些浅色装饰」，不影响功能。

**主题卡是微缩的应用界面，不是壁纸缩略图**：每张卡用**该主题自己的 token** 画出小侧栏、激活导航胶囊、内容条和强调色按钮，背景是该主题的图。卡片展示的是这个主题**对界面做了什么**，这是裁一张 JPEG 说不清的。卡片与缩略图的明暗、配色、背景全部取**应用当前模式**那一版，所以画廊里看到的就是切过去会得到的——不存在「预览一套、实际另一套」。

## 安装与卸载

安装走 GUI「插件 → 从本地目录安装」，选这个目录即可。

**装完即是「深海」主题**（配色 + 背景图 + 风格都生效）。想回官方外观点「恢复官方外观」。

卸载后运行时贡献全部撤销，且都有断言：

| 注册的东西 | 撤销方式 |
|---|---|
| token 覆盖层 | 卸载时撤销**活动**图层的 disposer |
| 两张注入样式表（页面 chrome、背景绘制 + Logo 规则） | 随插件 fiber 回收 |
| 设置页 | slot entry 销毁 |

唯一留存的是 `localStorage` 键 `dsh-skin-lab.settings`。旧版本写的 `dsh-skin-lab.skin` 会自动迁移（`ocean→abyss`、`sakura→ink`、`forest→pine`、`dusk→aurora`）。**首次启动不写任何东西**（有断言）。

### 为什么必须记住最新的 disposer

`overrideTokens` 返回的 disposer 只负责它那一次创建的图层。rc.2 产物原文：

```js
return () => {
  if (this.overrides.get(source) !== layer) return;   // 旧 disposer：空操作
  this.overrides.delete(source);
  this.publish();
};
```

文档原话：**「a no-op once the source has re-overridden」**。任何一次重组都会产生新图层，所以只记住第一次的话，活动图层无人拥有——卸载后主题留在原地、官方外观回不来。本插件用一个 `layerDispose` 指向活动图层，先撤销再重叠；套件用守恒律（`叠层次数 === 撤销次数 + 存活层数`）和专门的卸载场景盯着它，反向对照证明这些断言真的有牙齿。

## 资产流水线

内置背景图是本工作区用生图工具生成的，两步处理（产物都已提交）：

```sh
<python> scripts/prepare-assets.py   # 生成物 → 裁切 1600×900 → JPEG q82 → assets/（含 lightness.json）
node scripts/embed-assets.mjs        # assets/*.jpg + lightness.json → src/assets.js
```

质量取 82 而不是常用的 75：**平滑渐变正是 JPEG 出现色带的地方**，而这些图几乎没有高频细节，所以提高质量后依然压得很狠（20 张共 1117 KB，其中抽象十二张 339 KB、插画八张 778 KB）。脚本同时量出每张图的 **mean / p05 / p95** 明度写入 `assets/lightness.json`——运行时读不了 `data:` URL 的像素，而遮罩强度与可读性判断都依赖它；`p05/p95` 是必需的那两个统计量，因为决定可读性的是尾部而不是均值。一个 client bundle 只能是一个脚本，插件也没有路由去取同级文件，所以内置背景只能作为 `data:` URL 随包走——这也正是用户上传图片的形态，模型因此只有一种表示。最终产物 1.63 MB。

## 边界与已知不确定

- **自动压缩的浏览器端解码 / 编码路径没有端到端测过**：把文件喂给那个 `<input type=file>` 需要用户操作或 CDP，本机两条路都走不通。阶梯的形状、预算比较、档位折叠由纯函数断言，收敛性用**真实 JPEG 编码器**验证过，整条流程由桩 canvas 跑通——但"真浏览器里点一下会怎样"这一步需要你确认。（压缩本身已经在你的机器上跑通过一次：`2.1 MB → 18 KB（256 × 256）`。）
- **切换明暗模式时背景会换一张图**，因为每套主题两张图。这是设计，不是闪烁；画廊与缩略图会同步换。
- **用户上传的单张图在两种模式下共用**，靠自动遮罩保可读性。把「遮罩浓度」调到 0 会让浅色模式下只剩自动下限（约 0.56）——**再低就会影响可读性**，这也是这一档不设成完全手动的原因。
- **`color-scheme` 是选图依据**。若宿主从未设置它（非 DSH 环境），插件退回 `prefers-color-scheme` 媒体查询；两者都拿不到时按浅色处理，不会出现无背景。
- **「好不好看」仍然只有你能判断**：十套主题在浅色与深色下的渲染我都在真实应用里看过（画廊、缩略图、主界面背景、Logo 染色），可读性有 WCAG 断言兜底，但审美是另一个问题。不满意的话，改 `src/palettes.js` 里每个配色的 6 个锚点即可，其余 64 个 token 会自动跟着变；背景图则换 `assets/*.jpg` 并重跑两个脚本。
- **图片只在本机处理**，不上传网络。**超过存储预算的图片会被自动压缩**（见下面「上传过大时自己压」），只有超过 32 MB 才会拒绝——那个尺寸连解码都会卡住标签页。
- **自定义 Logo 会替换左侧图标**：用 `!important` 越过槽位锚点的内联 `display:contents`，把锚点变成 24×24 的盒子（槽位原本就为图标预留了这个位置），并把占位内容隐藏。相比原来图标自身的 24×17.66，盒子高了约 6px，属**实验性**选项（默认关闭）。
- **吸管只在 Chromium 系可用**（Electron 有），其他运行时自动隐藏。
- 页面用到 `color-mix()`、`aspect-ratio`、`:focus-visible`、`::file-selector-button`、`light-dark()`。前四个是装饰性的，不支持只是少些浅色；`light-dark()` 有普通深色纱兜底。
- **不接主题注册表**：主题不出现在内置「外观」列表里——那一行的选项是硬编码的 `light/dark/system`。
- **只覆盖颜色与上述结构项**，不改圆角与字体；`--dsw-static-*` 原语层未动。
